## Research question

Can parameter-efficient LoRA fine-tuning measurably improve a small,
permissively licensed instruction model on a narrow structured-output task,
compared with zero-shot **and** few-shot use of the unchanged base model, within
a free or low-cost compute budget?

## Hypothesis

Stated before training:

> Supervised LoRA fine-tuning on ~171 examples will substantially improve
> output-format compliance (valid JSON, correct enum values, no markdown
> fences), and will improve field-level accuracy on the fields determined by a
> learnable rule (`priority`) and by scenario semantics (`category`,
> `affected_service`). It will **not** reliably transfer to scenario families
> absent from training, because 171 examples across 32 scenarios is too few to
> learn the general concept behind each category.

The second half of that hypothesis is a prediction of *partial* failure, stated
in advance so it cannot be retrofitted to whatever happened.

## Task

IT helpdesk ticket triage. Input: one free-text ticket. Output: exactly one JSON
object with five keys.

```json
{"category": "network", "priority": "high", "affected_service": "vpn", "is_security_incident": false, "users_affected": 34}
```

Three closed enums (8, 4 and 10 values), one boolean, one positive integer.
Closed enums are deliberate: "the model invented a label that does not exist"
becomes a countable failure rather than a judgement call.

## Success criteria

Fixed in `src/forgelm/config.py::SUCCESS_CRITERIA` **before the first training
run** (DECISIONS.md D-008).

**Primary.** LoRA exact match on the frozen test split must exceed *both*
unchanged-model baselines, **and** the paired bootstrap 95% CI of the difference
against the **stronger** baseline must exclude zero.

**Secondary.** `schema_valid_rate` must not regress, and
`constraint_violation_rate` must not increase, against the stronger baseline.

Requiring the *stronger* baseline is the whole point. Zero-shot scored 0.0%
exact match; beating that proves nothing.

## Split procedure

Group-aware on `scenario_family`, stratified by `category` and severity rank.
Within each category the 7 families are ordered by `base_severity` (ties broken
by a seeded shuffle) and dealt with the fixed pattern
`[train, train, test, train, validation, test, train]`.

| Split | n | families |
|---|---|---|
| train | 171 | 32 |
| validation | 43 | 8 |
| test | 86 | 16 |

**The test split was frozen before training and read exactly once.** It is not
imported by `03_train_lora.py` at all.

## Baseline configurations

Both baselines use the **unchanged** base model, the **identical** system prompt
(SHA recorded per run), identical decoding and the identical parser.

| | Baseline A | Baseline B |
|---|---|---|
| Name | zero-shot | few-shot |
| Demonstrations | 0 | 8, one per category, **train split only** |
| Prompt length | 206-245 tokens | 965-1004 tokens |
| Decoding | greedy, `do_sample=False`, `num_beams=1` | same |
| `max_new_tokens` | 160 | 160 |
| Batch size | 8 | 8 |

`max_new_tokens=160` against a 35-38 token target is deliberate generosity: a
tight cap would convert base-model verbosity into "truncated" failures and
flatter the adapted model. Observed truncation rate was 0.0% in every condition.

## Pre-flight gates

All six passed before training (`reports/smoke_train.json`):

| Gate | Result |
|---|---|
| Tokenisation | 171 train / 43 val encoded |
| Truncation | 0 / 214, longest 281 vs limit 320 |
| Label masking | PASS on 214 examples, 0 problems |
| One-batch forward | loss 0.1855, finite, 76 supervised tokens |
| Tiny overfit | 0.1927 -> 0.00067 |
| Smoke training loop | completed, peak 2.14 / 4.00 GiB |

The forward-pass loss starting at ~0.19 is expected, not a bug: most tokens in
the target JSON are structural (`{"category": "`) and trivially predictable under
teacher forcing. This is exactly why generated exact match, not loss, is the
headline metric.

Every failure is retained in `runs/` with its traceback.

| Run | Failure | Resolution |
|---|---|---|
| `20260821T194748Z_build_dataset` | Dataset QC abort: ticket text for `email_spoofed_sender` contained the word "priority", leaking the label | Ask clause rewritten; the check that caught it is `check_priority_leak_terms` |
| `20260821T201457Z_smoke_train` | `CUDA error: out of memory` in `tiny_overfit` at batch 4 | 4 x 280 x 151,936 logits in fp16 + fp32 + gradients exceeds 4 GiB. Switched to gradient accumulation over micro-batches of 1 |
| `20260821T201722Z_smoke_train` | `AssertionError: EarlyStoppingCallback requires IntervalStrategy of steps or epoch` | The smoke config disables evaluation; the callback is now attached conditionally |

Two further defects were caught before they could produce a run at all: the
`str.capitalize()` acronym bug and four scope-contradicting clauses, both found
by manual review (D-013).

## Ethical considerations

- **Data.** Fully synthetic. No personal, medical, financial or legally
  sensitive content. Nothing scraped.
- **Licensing.** Base model is Apache-2.0 and ungated. No base-model weights are
  redistributed -- only the adapter, with a provenance file naming the exact base
  revision it requires.
- **Automated triage is consequential.** Mis-triaging a real security incident as
  `low` has real cost. This model must not be used on real tickets: it was
  trained on invented data against an invented priority rule, and no human
  factors, appeals process or error cost was modelled.
- **Not evaluated:** safety, alignment, fairness across demographic groups,
  robustness to adversarial input, or behaviour on out-of-domain text. Nothing
  is claimed about any of them.
- **Environmental cost** is small and stated honestly: a single consumer GPU for
  well under two hours in total.

### Determinism caveat

Full bit-exact determinism is **not** claimed. `torch.use_deterministic_
algorithms(True)` is deliberately not enabled: several fused kernels in the
training path have no deterministic implementation and would raise. cuDNN is set
deterministic and `benchmark` is disabled. In practice:

- Dataset generation, splitting, demonstration selection, bootstrap resampling
  and metric computation are **fully deterministic** and reproduce exactly.
- Greedy decoding is deterministic in practice.
- Training loss may differ in the last decimal places between runs on the same
  hardware, and more on different hardware.

Saying this is more useful than claiming determinism the setup cannot deliver.
