## Research question

Can parameter-efficient LoRA fine-tuning measurably improve a small,
permissively licensed instruction model on a narrow structured-output task,
compared with zero-shot **and** few-shot use of the unchanged base model, within
a free or low-cost compute budget?

## Hypothesis

Stated before training:

> Supervised LoRA fine-tuning on ~171 examples will substantially improve
> output-format compliance (valid JSON, correct enum values, no markdown
> fences), and will improve field-level accuracy on the fields determined by a
> learnable rule (`priority`) and by scenario semantics (`category`,
> `affected_service`). It will **not** reliably transfer to scenario families
> absent from training, because 171 examples across 32 scenarios is too few to
> learn the general concept behind each category.

The second half of that hypothesis is a prediction of *partial* failure, stated
in advance so it cannot be retrofitted to whatever happened.

## Task

IT helpdesk ticket triage. Input: one free-text ticket. Output: exactly one JSON
object with five keys.

```json
{"category": "network", "priority": "high", "affected_service": "vpn", "is_security_incident": false, "users_affected": 34}
```

Three closed enums (8, 4 and 10 values), one boolean, one positive integer.
Closed enums are deliberate: "the model invented a label that does not exist"
becomes a countable failure rather than a judgement call.

## Success criteria

Fixed in `src/forgelm/config.py::SUCCESS_CRITERIA` **before the first training
run** (DECISIONS.md D-008).

**Primary.** LoRA exact match on the frozen test split must exceed *both*
unchanged-model baselines, **and** the paired bootstrap 95% CI of the difference
against the **stronger** baseline must exclude zero.

**Secondary.** `schema_valid_rate` must not regress, and
`constraint_violation_rate` must not increase, against the stronger baseline.

Requiring the *stronger* baseline is the whole point. Zero-shot scored 0.0%
exact match; beating that proves nothing.

## Split procedure

Group-aware on `scenario_family`, stratified by `category` and severity rank.
Within each category the 7 families are ordered by `base_severity` (ties broken
by a seeded shuffle) and dealt with the fixed pattern
`[train, train, test, train, validation, test, train]`.

| Split | n | families |
|---|---|---|
| train | 171 | 32 |
| validation | 43 | 8 |
| test | 86 | 16 |

**The test split was frozen before training and read exactly once.** It is not
imported by `03_train_lora.py` at all.

## Baseline configurations

Both baselines use the **unchanged** base model, the **identical** system prompt
(SHA recorded per run), identical decoding and the identical parser.

| | Baseline A | Baseline B |
|---|---|---|
| Name | zero-shot | few-shot |
| Demonstrations | 0 | 8, one per category, **train split only** |
| Prompt length | 206-245 tokens | 965-1004 tokens |
| Decoding | greedy, `do_sample=False`, `num_beams=1` | same |
| `max_new_tokens` | 160 | 160 |
| Batch size | 8 | 8 |

`max_new_tokens=160` against a 35-38 token target is deliberate generosity: a
tight cap would convert base-model verbosity into "truncated" failures and
flatter the adapted model. Observed truncation rate was 0.0% in every condition.

## Pre-flight gates

| Gate | Result |
|---|---|
| Tokenisation | 171 train / 43 val encoded |
| Truncation | 0 / 214, longest 281 vs limit 320 |
| Label masking | PASS on 214 examples, 0 problems |
| One-batch forward | loss 0.1855, finite, 76 supervised tokens |
| Tiny overfit | 0.1927 -> 0.00067 |
| Smoke training loop | completed, peak 2.14 / 4.00 GiB |

The forward-pass loss starting at ~0.19 is expected, not a bug: most tokens in
the target JSON are structural (`{"category": "`) and trivially predictable under
teacher forcing. This is exactly why generated exact match, not loss, is the
headline metric.

## Ethical considerations

- **Data.** Fully synthetic. No personal, medical, financial or legally
  sensitive content. Nothing scraped.
- **Licensing.** Base model is Apache-2.0 and ungated. No base-model weights are
  redistributed -- only the adapter, with a provenance file naming the exact base
  revision it requires.
- **Automated triage is consequential.** Mis-triaging a real security incident as
  `low` has real cost. This model must not be used on real tickets: it was
  trained on invented data against an invented priority rule, and no human
  factors, appeals process or error cost was modelled.
- **Not evaluated:** safety, alignment, fairness across demographic groups,
  robustness to adversarial input, or behaviour on out-of-domain text. Nothing
  is claimed about any of them.
- **Environmental cost** is small and stated honestly: a single consumer GPU for
  well under two hours in total.

### Determinism caveat

Full bit-exact determinism is **not** claimed. `torch.use_deterministic_
algorithms(True)` is deliberately not enabled: several fused kernels in the
training path have no deterministic implementation and would raise. cuDNN is set
deterministic and `benchmark` is disabled. In practice:

- Dataset generation, splitting, demonstration selection, bootstrap resampling
  and metric computation are **fully deterministic** and reproduce exactly.
- Greedy decoding is deterministic in practice.
- Training loss may differ in the last decimal places between runs on the same
  hardware, and more on different hardware.

Saying this is more useful than claiming determinism the setup cannot deliver.

## Error analysis

**Failure taxonomy on the test split:**

| Failure mode | zero-shot | few-shot | LoRA |
|---|---|---|---|
| `correct` | 0 | 1 | 10 |
| `invalid_enum` | 15 | 33 | 18 |
| `out_of_range` | 2 | 0 | 0 |
| `wrong_type` | 45 | 0 | 0 |
| `wrong_values_only` | 24 | 52 | 58 |

The failure mode shifted, which is the signature of format learning without task
mastery. Zero-shot's dominant failure was `wrong_type` (45) -- structurally
malformed output, e.g. `affected_service: ["vpn", "email"]`. Under LoRA that
category is empty. What remains is `wrong_values_only` (58): well-formed,
schema-legal objects with incorrect values.

**Generalisation is the real limitation.** Exact match by held-out scenario
family:

| Family | correct / n |
|---|---|
| `ab_expense_reimbursement` | 5 / 5 |
| `ab_invoice_dispute` | 2 / 5 |
| `oth_meeting_room_av` | 1 / 5 |
| `sw_file_corrupt` | 1 / 5 |
| `am_account_lockout` | 1 / 6 |
| the remaining 11 families | **0** |

**11 of 16 held-out families produced zero fully correct outputs.** The
aggregate 11.6% is concentrated, not uniform. This was predicted in the
hypothesis above, before training.

**Remaining schema violations are copied nouns.** The 18 `invalid_enum` failures
are dominated by values lifted from the ticket text rather than mapped onto the
closed enum: `affected_service: "dns"` (6, for DNS-outage tickets), `"internet"`
(3), `category: "display"` (2), `"audio"` (2). Constrained decoding with a
grammar would make this class of failure impossible.

## Optional ablation -- training-data size (secondary, not pre-registered)

Run **after** the primary experiment was complete and reproducible. One variable
changed: 171 -> 86 training examples, category-stratified and deterministic.
Everything else identical -- rank, alpha, dropout, learning rate, schedule,
batch, sequence length, precision, seeds, prompt, decoding, evaluation split.

Run `20260821T215300Z_train_lora_d3e8b0`: 27.2 min, early stopping fired,
best checkpoint epoch 3, best validation loss 0.0824.

| Training examples | Schema valid | Exact match | category | priority |
|---|---|---|---|---|
| 86 (50%) | 82.6% | 17.4% | 67.4% | 57.0% |
| **171 (100%)** | 79.1% | 11.6% | 53.5% | 46.5% |

| Comparison | Difference | 95% CI | p | Verdict |
|---|---|---|---|---|
| exact match | -5.8 pp | [-12.8, +1.2] | 0.180 | not distinguishable from zero |
| schema valid | -3.5 pp | [-11.6, +4.7] | 0.581 | not distinguishable from zero |
| `category` | **-14.0 pp** | [-22.1, -7.0] | **0.0005** | difference detected, favouring *less* data |

**What was actually removed.** 31 of 32 scenario families retained;
`email_dl_update` lost entirely as a side effect of stratifying by category
rather than by family. Examples per family 5.34 -> 2.77. So this is a ~52%
depth cut at 97% coverage, not a pure depth cut. The confound is small but real
and is not rounded away.

**Interpretation.** Doubling the data produced no detectable change in the
headline metric. Combined with 11 of 16 held-out families scoring zero, this
points at **scenario coverage rather than example volume** as the binding
constraint. The significant `category` result in favour of *less* data admits
two explanations this experiment cannot separate: overfitting to the 32
training scenarios (5.3 repetitions vs 2.8), or single-seed run-to-run variance.
It is recorded as a hypothesis requiring 3-5 seeds per arm to settle.

**The headline result is unchanged.** The ablation arm scored higher, and it is
deliberately not promoted. It was not pre-registered; substituting a post-hoc
arm because it scored better would convert the frozen test split into a
model-selection set and void the primary number.

## Conclusion

**The research question is answered: yes, within this narrow setting.** LoRA
fine-tuning of Qwen2.5-0.5B-Instruct on 171 synthetic examples produced a
statistically detectable improvement over both unchanged-model baselines on the
frozen test set, including over a strong few-shot baseline, and all four
pre-declared success criteria were met.

**The improvement is mostly format compliance, not task competence.** The
adapter reliably learned the output contract -- 100% strict JSON, schema validity
61.6% -> 79.1%, zero structurally malformed outputs -- and learned the task only
partially. Two of five fields improved significantly, two showed no detectable
difference, and one was already saturated.

**Generalisation to unseen scenarios largely did not happen**, exactly as
hypothesised. That is the honest headline, and it points at the next experiment:
broader scenario coverage rather than more examples per scenario.

**The ablation supports that reading.** Halving the training data produced no
detectable change in exact match (p = 0.18), so at this scale the binding
constraint is not how many examples the model sees but how many distinct
situations they cover. The next experiment should add scenario families, not
examples per family.

Nothing here supports any claim about real helpdesk tickets, deployment, safety,
or behaviour outside this 86-example synthetic test set.

Raw per-example predictions for every condition are in
`reports/predictions/*.jsonl`. Every reported metric can be recomputed from
them without a GPU; `scripts/06_audit.py` does exactly that and fails if any
recomputed value disagrees with what was recorded at run time.
