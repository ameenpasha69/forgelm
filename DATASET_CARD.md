## Purpose

Training and evaluation data for a single question: can LoRA fine-tuning improve
a small instruction model on a narrow structured-output task, compared with
zero-shot and few-shot prompting of the same unchanged model?

The dataset exists to make that question *answerable*, which means every label
must be objectively checkable and every generalisation claim must be testable.
It is not intended to represent real helpdesk traffic.

## Origin and licence

100% synthetic, generated programmatically. **No real tickets, no scraped text,
no personal data, no medical, financial or legally sensitive content.** Nothing
was copied from an external corpus, so there is no upstream licence to inherit.
Released under MIT alongside the code.

## Task

Input: one free-text IT helpdesk ticket.
Output: one JSON object with exactly five keys, in a fixed order.

```json
{"category": "network", "priority": "high", "affected_service": "vpn", "is_security_incident": false, "users_affected": 34}
```

| Field | Type | Values |
|---|---|---|
| `category` | enum(8) | `access_management`, `hardware`, `network`, `software`, `security`, `account_billing`, `email`, `other` |
| `priority` | enum(4) | `low`, `medium`, `high`, `critical` |
| `affected_service` | enum(10) | `vpn`, `email`, `crm`, `printer`, `laptop`, `wifi`, `payroll`, `database`, `phone`, `none` |
| `is_security_incident` | boolean | `true` / `false` (not `0`/`1` -- the validator rejects ints) |
| `users_affected` | integer | `>= 1` |

## Generation procedure

Two orthogonal axes are composed:

**Scenario family (56).** A recurring situation, e.g. `net_vpn_drops`,
`hw_battery_swelling`, `sec_ransomware_note`. A family fixes `category`,
`affected_service`, `is_security_incident` and a `base_severity` (0-3), and
supplies 4 symptom clauses, 4 detail clauses and 4 ask clauses. Exactly 7
families per category.

**Template family (8).** A surface writing style: `terse`, `polite_request`,
`frustrated`, `formal_ticket`, `chat_style` (lower-case, light typos),
`manager_escalation`, `narrative`, `bulleted`. Template families carry **no**
label information.

Each example samples a symptom, a detail, an ask, a user-count scale and a
template, all from a per-example seed derived by SHA-256 from
`(seed_name, family_id, index)`. That derivation is why regenerating example 42
gives identical text regardless of how many examples precede it.

### How `priority` is determined

`priority` is *not* stored per family -- it is computed by a fixed rule, so the
model must infer it from the text rather than memorise it:

```
score = base_severity                      # 0..3, a property of the scenario
if is_security_incident:      score += 1
if users_affected >= 50:      score += 2
elif users_affected >= 10:    score += 1

score >= 5 -> critical    >= 3 -> high    >= 2 -> medium    else -> low
```

Because `users_affected` varies within a family, one scenario family produces
several different priorities. A model cannot succeed by learning
"family X is always high"; it has to read the number out of the text and apply
the bump rule. Every label is verified against this rule at build time
(`check_priority_rule`).

### How `users_affected` stays recoverable

Every ticket either states the exact integer ("About 34 people are affected.",
"So far 12 people have reported it.") or is unambiguously about one person
("Only one person is affected."). A build-time check (`check_users_recoverable`)
fails if a label cannot be recovered from the text, because an unguessable label
makes the metric unfair rather than difficult.

## Splitting

**Group-aware on `scenario_family`, stratified by `category` and severity rank.**

Within each category the 7 families are ordered by `base_severity` (ties broken
by a seeded shuffle) and dealt using the fixed pattern
`[train, train, test, train, validation, test, train]` indexed by severity rank.

This gives 4 train / 1 validation / 2 test families per category, so:

- **No scenario family appears in more than one split.** The test set contains
  situations the model has never been trained on -- that is the generalisation
  axis under test.
- Every category appears in every split, so macro-F1 is defined everywhere.
- Every priority class appears in every split. The earlier plain-shuffle version
  produced a validation split with zero `critical` examples; see DECISIONS.md
  D-006 for why that was changed and when.

The manifest maps every `example_id` to a split and is checksummed. Loading it
re-verifies the checksum and refuses to proceed on a mismatch, so a silently
altered split cannot flow into a result.

## Leakage controls

| Check | Result |
|---|---|
| Exact duplicate text | 0 |
| Normalised duplicate text | 0 |
| Scenario family spanning splits | 0 |
| Cross-split near-duplicates at Jaccard >= 0.80 | **0** |
| Maximum observed cross-split similarity | **0.3255** |
| Priority-revealing terms in ticket text | 0 |
| Single-user examples contradicted by their own clauses | 0 |

The near-duplicate scan is exhaustive -- all 44,850 cross-split pairs compared
on character 4-gram Jaccard, not sampled or approximated. A test asserts the
maximum stays below 0.60, so the *margin* is monitored rather than just the
threshold.

**Template families deliberately span splits.** They are writing styles with no
label content; holding one out would measure "can it handle unfamiliar prose",
which is a different question. This is stated explicitly rather than left for a
reader to discover, and the near-duplicate scan is the evidence that sharing
styles did not create textual overlap.

## Manual review

An automated build passing is not the same as a human having looked. A
stratified sample (one example per category per split) was read by hand. Round 1
found four defects that the automated checks had not been written to catch:

1. `str.capitalize()` lower-cased everything after the first character, turning
   "the CRM" into "the crm" and "I try" into "i try". Fixed; a regression test
   now guards it.
2. Four detail clauses asserted other people were affected while the label said
   `users_affected = 1`. Rewritten; `check_scope_consistency` now fails the
   build if one reappears.
3. `email_spoofed_sender` contained the ask "treat this as a priority please",
   leaking a priority term. Caught automatically on the first build and
   rewritten.
4. Awkward singular scope phrasing on request-type tickets; a neutral variant
   was added.

Every record carries `qc_status: "auto_validated"`, meaning it passed all
automated checks. Clause-level lineage (`symptom_text`, `detail_text`,
`ask_text`, `scope_text`) is stored on every record so any example can be traced
to its source fragments without re-running the generator.

## Known biases and limitations

These are real and are not worked around, because working around them would make
the dataset less honest rather than better:

- **Urgency language correlates with severity.** High-severity scenarios
  naturally use urgent phrasing ("we need this restored urgently"). That is
  realistic, but it means a model can pick up part of `priority` from tone
  rather than from the severity/blast-radius rule. The rule still requires
  reading `users_affected`, so tone alone is insufficient -- but it is a shortcut
  and it is disclosed.
- **`affected_service: none` is 57% of the data.** A model that always predicted
  `none` would score 57% on that one field.
- **Only 3 `medium` examples in the test split.** Priority macro-F1 is
  correspondingly noisy. This is a consequence of the priority rule (a score of
  exactly 2 is rare), and rebalancing the labels to flatter the metric was
  rejected.
- **British English, corporate register, one domain.** No multilingual coverage,
  no informal consumer support, no non-Western naming or office conventions.
- **Templated construction.** Real tickets are messier, longer, contain
  irrelevant detail, and frequently omit the information needed to label them.
  Every ticket here is answerable by construction; real ones are not.
- **56 scenarios is a narrow world.** The test set covers 16 held-out scenarios.
  Good test performance demonstrates generalisation to *those* 16, not to
  helpdesk tickets in general.
- **Labels are correct by construction, not by consensus.** There is no
  inter-annotator agreement figure because there were no annotators. That
  removes annotation noise, and also removes any evidence that the label scheme
  matches how real triage staff would decide.

## Intended use

- Reproducing this LoRA adaptation experiment.
- Teaching structured-output evaluation, leakage control, and group-aware
  splitting.
- A benchmark harness for small-model JSON-schema compliance.

## Prohibited / out-of-scope use

- **Do not use this to triage real helpdesk tickets.** The data is synthetic and
  the priority rule is invented for the experiment.
- Do not treat measured accuracy here as predictive of accuracy on real tickets.
- Do not use it to make claims about model safety, alignment, fairness or
  robustness. It was not designed to measure any of those.
- Do not use it as a general-purpose instruction-tuning corpus.
