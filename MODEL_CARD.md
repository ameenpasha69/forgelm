# Model card -- ForgeLM ticket-triage LoRA adapter v1.0.0

**This is a LoRA adapter, not a model.** It is a set of low-rank weight deltas
that must be loaded on top of a specific base model. On its own it does nothing.
No foundation model was created, trained or redistributed here.

---

## What it is

| | |
|---|---|
| Artefact | LoRA adapter (PEFT) |
| Location | `artifacts/lora_adapter/` |
| Trainable parameters | 8,798,208 (1.7497% of the base model) |
| Adapter rank | r = 16, alpha = 32, dropout = 0.05 |
| Adapted modules | `q_proj`, `k_proj`, `v_proj`, `o_proj`, `gate_proj`, `up_proj`, `down_proj` (all 24 layers) |
| Adapter licence | MIT (this repository) |

## Required base model

The adapter is useless without it, and will not load against anything else:

| | |
|---|---|
| Model | `Qwen/Qwen2.5-0.5B-Instruct` |
| **Revision** | `7ae557604adf67be50417f59c2c2f167def9a775` |
| Licence | apache-2.0 (governs use of the base weights) |

The revision is pinned to a commit hash. Loading against a different revision is
untested and unsupported. `artifacts/lora_adapter/forgelm_provenance.json`
records the required base model, its revision, the dataset checksum, the split
manifest checksum and every seed.

**No base-model weights are redistributed in this repository.**

## Intended task

Convert one free-text IT helpdesk ticket into a strict five-field JSON object:

```json
{"category": "network", "priority": "high", "affected_service": "vpn", "is_security_incident": false, "users_affected": 34}
```

`category` is one of 8 values, `priority` one of 4, `affected_service` one of 10,
`is_security_incident` is a boolean, `users_affected` a positive integer. The
exact contract is in `src/forgelm/schema.py`.

The adapter was trained with one specific system prompt. Using a different
prompt is out of distribution and the format compliance it was trained for may
not hold.

## How to load it

```python
from transformers import AutoTokenizer, AutoModelForCausalLM
from peft import PeftModel
import torch

BASE = "Qwen/Qwen2.5-0.5B-Instruct"
REV  = "7ae557604adf67be50417f59c2c2f167def9a775"

tokenizer = AutoTokenizer.from_pretrained(BASE, revision=REV)
base = AutoModelForCausalLM.from_pretrained(BASE, revision=REV,
                                            dtype=torch.float16).to("cuda")
model = PeftModel.from_pretrained(base, "artifacts/lora_adapter")
model.eval()

# Build the prompt exactly as the adapter was trained -- same system prompt,
# same official chat template. This helper does both.
from forgelm.prompts import render_prompt

prompt = render_prompt(tokenizer, "The VPN keeps dropping. 14 users affected.")
inputs = tokenizer(prompt, return_tensors="pt",
                   add_special_tokens=False).to(model.device)

with torch.no_grad():
    out = model.generate(**inputs, max_new_tokens=160, do_sample=False,
                         eos_token_id=tokenizer.eos_token_id)

print(tokenizer.decode(out[0][inputs["input_ids"].shape[1]:],
                       skip_special_tokens=True))
```

`forgelm.modeling.load_adapted_model()` does the same thing and additionally
**verifies the adapter is active** -- it raises if the LoRA weights are all zero,
which would silently reproduce base-model behaviour.

## Training data

171 examples from the training split of `forgelm-ticket-triage` v1.0.0 --
synthetic IT helpdesk tickets generated by this repository. See
`DATASET_CARD.md`.

- Fully synthetic. No real tickets, no personal data, no scraped text.
- 32 scenario families. The 16 test families were never seen during training.
- Dataset sha256 `63c56f5045...`, split manifest checksum `994141c6e0...`.

## Training procedure

Supervised fine-tuning on prompt/completion pairs with the **prompt masked**
(labels `-100` over prompt positions), so the loss is computed only over the JSON
answer. Effective batch 8 (1 x 8 accumulation), lr 2e-4, cosine schedule with
10% warm-up, up to 8 epochs with early stopping on validation loss (patience 3),
fp16 autocast with a gradient scaler and fp32 LoRA parameters, `max_seq_len` 320
with zero truncation.

Checkpoint selected by **validation loss**, then confirmed by a generative
evaluation on the validation split. Test data was never used for any selection.

Full configuration and the reproducibility ledger: `EXPERIMENT_CARD.md` and
`runs/`.

## Evaluation scope

Evaluated on 86 held-out synthetic examples drawn from 16 scenario families that
appear in no training example, against two unchanged-model baselines
(zero-shot and few-shot k=8) using an identical prompt, identical greedy decoding
and an identical parser.

Metrics, confidence intervals, paired significance tests and the failure
taxonomy: `reports/RESULTS.md`. Raw per-example predictions:
`reports/predictions/*.jsonl`.

**That is the entire evaluation.** It is one narrow benchmark on one synthetic
dataset with 86 test examples.

## Limitations

- **Synthetic training and evaluation data.** Nothing here predicts behaviour on
  real helpdesk tickets, which are messier, longer, frequently missing the
  information needed to label them, and not drawn from 56 tidy scenarios.
- **86 test examples.** Confidence intervals are wide. Small differences are not
  interpretable.
- **Only 3 `medium` priority examples in the test set**, so priority macro-F1 is
  noisy.
- **One prompt.** Format compliance is tied to the system prompt it was trained
  with.
- **English only**, British corporate register, one organisational culture.
- **The priority rule is invented** for this experiment. It is not how any real
  service desk prioritises work.
- **One configuration, one seed.** No hyperparameter search, no multi-seed
  variance estimate. A single training run is a sample of size one.
- **Not evaluated for** safety, alignment, fairness, robustness, adversarial
  input, prompt injection, latency under load, or any out-of-domain behaviour.

## Out-of-scope and prohibited use

- **Do not use this to triage real helpdesk tickets**, and especially not to
  decide whether something is a real security incident. Mis-classifying a real
  incident as `low` has real cost, and this adapter was trained on invented data
  against an invented rule.
- Do not use it as a general-purpose assistant. It was fine-tuned to emit one
  JSON schema and nothing else.
- Do not treat its `is_security_incident` output as a security control.
- Do not deploy it in any automated decision path affecting a person.

## What was NOT done

Stated explicitly because absence of a claim is easy to miss:

- No quantisation. This is **LoRA**, not QLoRA.
- No RLHF, DPO or any human-preference optimisation.
- No retrieval augmentation.
- No distributed training, no vLLM, no experiment-tracking service.
- No agentic or tool-use capability.
- No claim of production readiness, deployment readiness, improved safety,
  alignment, fairness, robustness, reduced latency or reduced cost. None of
  those were measured.
