## Why v2 exists

v1's test split was used to report the headline result, so it has been seen.
Any further development decision taken against it would turn it into a
model-selection set and quietly destroy the meaning of the number.

v2 supplies scenario families that no ForgeLM model has trained on, frozen
before use.

## What is deliberately unchanged

The task, the output schema, the prompt, the priority rule and the generation
machinery are inherited from v1 **without modification**. Only the scenario
catalogue is new. A v2 result is comparable to a v1 result precisely because
nothing except the situations changed.

## These are new situations, not reworded old ones -- measured

Every v2 ticket was compared against every v1 ticket on character 4-gram
Jaccard similarity:

| | |
|---|---|
| Comparisons | **57,600** (192 x 300), exhaustive |
| **Maximum similarity to any v1 ticket** | **0.3313** |
| Scenario-family name overlap with v1 | **none** |

The build script refuses to proceed if any v2 ticket reaches 0.80 similarity to
a v1 ticket, or if any family name is reused. "Not a paraphrase" is a
measurement here, not a claim.

Examples of the difference in kind: v1 had `net_dns_failure`; v2 has
`v2_net_ipv6_misconfig` (hosts preferring a broken IPv6 route) and
`v2_net_rogue_ap` (an unauthorised access point impersonating the corporate
SSID). v1 had `sec_phishing_email`; v2 has `v2_sec_mfa_fatigue` (push-approval
spam) and `v2_sec_insider_download` (a leaver bulk-copying files).

### The priority-balance fix

v1's test split held **3** `medium` examples. Priority macro-F1 on it was close
to meaningless.

Changing the priority rule would have fixed the balance and destroyed
comparability with v1. So the **rule is unchanged**; instead family severities
and user-count scales were chosen so that score-2 combinations (which produce
`medium`) occur often:

```
severity 1 + 10-49 users        severity 2 + fewer than 10 users
severity 0 + 50+ users          severity 1 + security + fewer than 10 users
```

| | v1 | v2 |
|---|---|---|
| `medium` share of dataset | 12.7% | **31.8%** |
| `medium` in the test split | **3** | **17** |

## Splits

Group-aware on `scenario_family`, stratified by category and severity rank.
Pattern indexed by severity rank within each category:
`[train, test, validation, test]` -- so the test arm spans mid and high severity
rather than clustering at one end.

| Split | n | families | priorities | |
|---|---|---|---|---|
| train | 48 | 8 | high 8, low 26, medium 14 | |
| validation | 48 | 8 | critical 2, high 10, low 6, medium 30 | |
| **test** | **96** | **16** | **critical 30, high 18, low 31, medium 17** | **SEALED** |

**Known limitation, stated rather than discovered later.** With 4 families per
category and 1 allocated to train, the training split necessarily receives a
single severity rank per category and therefore contains **no `critical`
examples**. That is structural, not an oversight: v2's purpose is the sealed
evaluation surface, and 96 test examples were preferred over a more usable
48-example training split. Anyone training on v2 should combine it with v1 data.

## The seal

The test split is sealed in code, not by convention:

- `splits_v2.assert_not_sealed()` **raises** if a training or
  demonstration-selection path touches a sealed example.
- The manifest carries a dedicated `test_membership_checksum`, verified on
  every load by `load_manifest_v2`. It answers exactly one question -- "is this
  the same set of sealed examples?" -- so unrelated manifest edits cannot
  invalidate it and a quiet change to what is sealed cannot hide.
- CI re-verifies the seal on every push.

**Seal policy.** v2 test predictions are not inspected until configurations,
seeds, prompts, decoding and checkpoint-selection rules are frozen and
committed.

## Known biases and limitations

Inherited from v1 and still true:

- Synthetic, templated, British English, corporate register, one domain.
- Urgency language correlates with severity, which a model can partly exploit.
- Labels are correct by construction, so there is no inter-annotator agreement
  figure -- which removes annotation noise and also removes any evidence that
  the label scheme matches how real triage staff would decide.

New to v2:

- The training split contains no `critical` examples (see above).
- 32 families is still a narrow world. Good performance on the 16 sealed test
  families demonstrates generalisation to *those*, not to helpdesk tickets.

## Intended and prohibited use

**Intended:** a sealed evaluation surface for ForgeLM adaptation experiments;
teaching sealed-test discipline and cross-version leakage checking.

**Prohibited:** triaging real helpdesk tickets; any claim about safety,
alignment, fairness or real-world reliability; treating accuracy here as
predictive of accuracy on real tickets.
